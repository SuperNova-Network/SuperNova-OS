# Architecture

How SuperNova OS turns "type an address" into a loaded page, and why each piece exists.

## The path of a request

```
 Browser tab                                              Your server
┌───────────────────────────┐                  ┌──────────────────────────────┐
│ Desktop (index.html)      │                  │ app.js (Express)             │
│  └ Browser window         │                  │  ├ static files, /api/*      │
│     └ page (iframe)       │   1. fetch       │  ├ generated proxy configs   │
│                           │ ───────────┐     │  └ /wisp/  (WebSocket)       │
│ Service worker (sw.js)    │            │     │         │                    │
│  ├ /service/…  Ultraviolet│  2. rewrite│     │         │ 5. TCP / TLS       │
│  └ /scram/…    Scramjet   │            ▼     │         ▼                    │
│                           │   3. bare-mux    │   the website                │
│ bare-mux SharedWorker     │ ──────────────── │                              │
│  └ libcurl or Epoxy       │   4. Wisp over   │                              │
└───────────────────────────┘      WebSocket   └──────────────────────────────┘
```

1. Something in the page (an iframe navigating, a script calling `fetch`) requests a URL under a **proxy prefix**: `/service/…` for Ultraviolet or `/scram/…` for Scramjet.
2. The **service worker** (`public/sw.js`) intercepts it. The selected engine rewrites the request and, later, the response (HTML, CSS, JavaScript, headers, cookies) so the site works from this origin.
3. The engine hands the request to **bare-mux**, which forwards it to a `SharedWorker` that owns the **transport**.
4. The transport (**libcurl** or **Epoxy**, both implementing TLS in WebAssembly in the browser) speaks the **Wisp** protocol over a single WebSocket to `/wisp/`.
5. The server's Wisp implementation opens the real TCP connection. This is where the [content filter](CONFIGURATION.md#content-filter) and the private-network guard are enforced, for every connection from every engine.

Everything non-proxied (the desktop itself, `/api/*`) is left to the browser; the worker does not call `respondWith` for it.

## Files

| Path | What it is |
| --- | --- |
| `app.js` | The server: Express, the Wisp WebSocket, generated configs, static asset mounts |
| `config.js` | Server settings (reads environment variables); the single source of truth for URL prefixes |
| `src/policy.js` | The content filter's rules (pure, unit-tested) |
| `public/sw.js` | The service worker |
| `public/proxy/core.js` | `SnProxy`: starts everything and picks the engine. Used by every page |
| `public/proxy/store.js` | `SnStore`: settings in `localStorage` with change events across windows |
| `public/proxy/resolve.js` | `SnResolve`: "is this an address or a search?" |
| `public/proxy/boot.html` | The page served when a proxied URL arrives without the worker |
| `public/proxy/scramjet-db.js` | Creates Scramjet's database schema safely (see below) |
| `public/apps/browser.*` | The SuperNova Browser |
| `public/apps/settings.*` | The Settings app |
| `public/resources/scripts/main.js` | The desktop shell (windows, taskbar, launcher): legacy code, kept working |
| `public/resources/scripts/cloak.js` | Tab disguise, panic key, `about:blank` launcher |
| `public/resources/css/` | `tokens.css` (design tokens), `components.css` (apps), `fx.css` (ripple), `theme.css` (desktop), `styles.css` (legacy desktop) |

Some URLs are *generated by the server* from `config.js` so the prefixes live in one place: `/proxy/config.js`, `/proxy/uv.config.js`, `/proxy/scramjet.config.js`. The proxy libraries themselves are served straight from `node_modules` (`/assets/uv/`, `/assets/scramjet/`, `/baremux/`, `/libcurl/`, `/epoxy/`), so updating a dependency updates the proxy; nothing is vendored.

## The first visit, and why it used to return 404

A service worker only controls requests *after* it is active. The original code registered the worker and navigated to `/supernova/…` immediately; on a fresh visit the request reached the server, which answered 404. Going back and trying again worked because the worker had activated by then. Desktop apps (YouTube, Reddit) never registered the worker at all.

Three layers now prevent this:

1. `SnProxy.ready()` registers the worker and waits for the **activated** state, connects the transport, and initialises the engine. Every navigation goes through it.
2. The worker calls `skipWaiting()` and `clients.claim()`, so a new version takes over immediately.
3. If a navigation under a proxy prefix *still* reaches the server (cleared site data, a shared link, a new device), the server answers with `boot.html` instead of a 404. That page starts the worker and reloads, with a loop guard that gives up after three attempts and explains why. Subresource requests still get a real 404, so HTML is never served as a script.

## Workarounds for upstream bugs

These are small, commented in the code, and worth knowing about when upgrading dependencies.

**Scramjet's database race** (`public/proxy/scramjet-db.js`). Scramjet's worker opens its IndexedDB database without a schema upgrade handler; the page-side controller creates the object stores in its own. If the worker wins the race, the database exists without stores and `init()` fails. The helper creates the stores first (and repairs a database already in that state) before either side touches it.

**Scramjet's config singleton** (`public/sw.js`). When the page pushes its config to a worker that controls it, Scramjet stores it but skips initialising an internal singleton, and every request then throws "reading 'prefix'". The worker forces one real load from IndexedDB per lifetime.

**libcurl's start-up race** (`public/proxy/core.js`). bare-mux calls `init()` on each request until the transport is ready, and libcurl's `init()` builds a session before its WebAssembly has loaded, so the first request of a visit could fail with "wasm not loaded yet" (about one fresh visit in five). The transport is installed through a subclass with one shared, retrying `init()`.

**Scramjet's cookie acknowledgement** (`public/sw.js`). For a Set-Cookie on a sub-resource, Scramjet messages the page and waits for its reply before returning the response. A page cannot receive that message until `DOMContentLoaded`, and a parser blocked on a stylesheet or script cannot reach it until that same response arrives, so pages whose sub-resources set cookies (Wikipedia, GitHub, most large sites) hung forever while tiny pages worked. The worker keeps its own cookie store, so it now delivers the message without waiting.

**Scramjet frames** (`SnProxy.registerFrame`). Scramjet expects iframes to be named by its `ScramjetFrame` helper; without it, pages nested inside other frames raised an error from Scramjet's bootstrap.

**Favicons** (`public/apps/browser.js`). Reading `link.href` from a proxied document returns the *real* URL, so using it directly would load the icon from the site and bypass the proxy. Icons are re-encoded through the proxy.

## Settings flow

Preferences live in `SnStore` (`localStorage` keys prefixed `sn.`). Writing one notifies listeners in the same window and, through the browser's `storage` event, every other window of the origin, so the Settings window can retune the cloak, the proxy and the Browser live with no wiring between them. Desktop-only options (colour scheme, wallpaper, window size, time zone) go through `window.SnOS`, a small bridge the desktop exposes to its own windows.

## Known limits

- Proxied pages are same-origin with the desktop (that is how service-worker proxies work). The engines virtualise storage and `location` for each site, but treat a proxied page as sharing a browsing context with the desktop.
- The desktop's geometry is built on `vw` units, so below about 760 px wide it shows links to the (responsive) Browser and Settings instead of the desktop.
- Cross-origin pages embedded in windows (the bundled games on `picturelements.github.io`) are not proxied; the panic key cannot see key presses inside them.
